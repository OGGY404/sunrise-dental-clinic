## 2. Branching strategy

A simplified Git Flow. It is deliberately small, because this is a solo project —
a large team model would add ceremony without adding value, and the report says so.

```
main      ●────────────────●───────────────────●        stable, tagged releases
           \              /                   /
develop     ●──●──●──●───●──●──●──●──●──●────●          integration branch
             \    /       \       /   \    /
feature/*     ●──●         ●─────●     ●──●             one branch per feature
```

| Branch | Purpose | Rule |
|---|---|---|
| `main` | Always working. Every commit here is a version that runs. | Only ever updated by merging `develop`. Tagged on release. |
| `develop` | Where finished features are combined and tested together. | Feature branches merge in here first. |
| `feature/<name>` | One branch for one piece of work. | Branched from `develop`, merged back by pull request, then deleted. |
| `fix/<name>` | A bug found after a feature was merged. | Same life cycle as a feature branch. |

**Why branch at all on a solo project?** If a feature turns out badly it can be
abandoned by deleting its branch, leaving `develop` untouched. It also produces
the pull requests and merge commits the assessment asks to see.

## 3. Commit message convention

[Conventional Commits](https://www.conventionalcommits.org/): a type, then a short
summary in the imperative mood, then a body explaining **why** rather than what.

```
<type>: <what changed, in the imperative>

<why it changed, and anything a reader would not guess>
```

| Type | Used for |
|---|---|
| `feat` | A new feature the user can see |
| `fix` | A bug fix |
| `test` | Adding or correcting tests |
| `refactor` | Restructuring code without changing behaviour |
| `docs` | Documentation only |
| `chore` | Build files, configuration, tooling |
| `ci` | GitHub Actions workflow |

**Good:**

```
feat: prevent double booking with a unique slot index

A Java check alone loses a race when two receptionists save at the same
instant. slot_key is now a generated column holding dentist|date|time, or
NULL when cancelled, with a UNIQUE index over it. The database therefore
rejects the second booking, and a cancelled slot is instantly rebookable
because SQL permits many NULLs in a unique index.
```

**Bad:** `update`, `fixed stuff`, `changes`, `asdf` — these tell a marker nothing.

## 4. Test-driven development in the history

The brief asks for evidence that TDD was actually used. The git history is that
evidence, so tests are committed **before** the code that satisfies them:

```
test: add failing tests for bill calculation      <- red
feat: implement bill calculation service          <- green
refactor: extract billing rules into strategies   <- refactor
```

Each red-green-refactor cycle is three commits, and the report cites the commit
hashes for at least one full cycle.

## 5. Tags and releases

Semantic versioning, tagged on `main`:

| Tag | Meaning |
|---|---|
| `v0.1.0` | Database layer complete |
| `v0.2.0` | Domain and service layer complete |
| `v0.3.0` | REST API and security complete |
| `v0.4.0` | Web interface complete |
| `v1.0.0` | Version submitted for assessment |

```powershell
git tag -a v0.1.0 -m "Database layer: schema, procedures, triggers"
git push origin v0.1.0
```

## 6. Pull requests

Even working alone, every feature branch merges through a pull request, because
the PR is where the reasoning gets written down and it is assessed evidence.

Each PR states: what it does, which requirement (FR1–FR7) it satisfies, how it
was tested, and anything left undone. Merged with `--no-ff` so the merge commit
survives and the branch is visible in the history graph.

## 7. What `.gitignore` excludes, and why

| Ignored | Reason |
|---|---|
| `target/` | Build output. Regenerated by `mvn package`; committing it bloats the repository. |
| `.env` | **Contains the real database password.** Committing a credential to a public repository is a serious security mistake. `.env.example` is committed instead, with placeholder values. |
| `.idea/`, `.vscode/`, `*.iml` | Personal editor settings. Not part of the program. |
| `*.log` | Runtime noise, different on every machine. |
| `application-local.properties` | Local overrides that may contain credentials. |

`.gitattributes` is also committed, forcing LF line endings in the repository so
files edited on Windows do not appear "completely rewritten" to the Linux build
server on GitHub Actions.

The first commit is on `main` because a repository needs one commit before any
branch can be made from it. Every feature after this one follows the full
cycle: branch from `develop`, work, pull request, merge back.

`main` deliberately sits behind `develop`. `main` only moves at a release, so
the newest documentation commit waits on `develop` until the next tag.

> **Note for the report:** the assessment rewards commits spread across several
> days, showing the system growing a piece at a time. Keep committing on the day
> the work is actually done rather than saving it all until the end — a history
> created in one sitting is obvious to a marker and cannot be repaired later.
